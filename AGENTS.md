# GratiaVR — обязательные правила работы в проекте

Эти правила действуют для всех чатов и агентов, работающих в этой папке.
Прямое указание пользователя имеет приоритет. Не требовать повторного разрешения
на уже согласованную работу; новые архитектурные решения делать конкретными и проверяемыми.

## Цель и текущие ограничения

- PC VR на Unreal Engine 5.8.3 / OpenXR / SteamVR; самостоятельная Win64-сборка.
- Общая логика должна поддерживать замену персонажа без переписывания компонентов.
- Текущая сцена рассчитана на одного персонажа и ровный пол. Расширения вводить явно.
- Не объявлять ходьбу, реальные касания, совпадение поверхности или 90 FPS проверенными
  только по наличию кода, настольному тесту, demo-реакции или частоте дисплея.
- Отличать «реализовано», «прошло автоматический тест», «проверено на реальном VR-вводе».

## Blender и исходники модели

- Подготовку/изменение модели, рига, морфов, анимаций и экспорт из Blender выполнять
  через Blender MCP в открытой рабочей копии. Python через execute_blender_code
  допустим: транспорт выполнения обязан быть MCP.
- Не запускать отдельный фоновый Blender для изменения модели или экспорта в обход MCP.
  При недоступности MCP сохранить работу и сообщить конкретное ограничение.
- Не изменять Gratia.blend, Gratia_source.blend, Gratia_working.blend и их резервные копии.
  Редактируемая MVP-копия — Exports/Gratia/Gratia_mvp.blend.
- Перед изменением экспорта проверять рабочий файл и сохранять исходные SHA-256.
- Валидировать новые клипы/корректирующие формы относительно исходной evaluated-модели:
  целые и промежуточные кадры, стопы/корень, максимальная ошибка вершин.
- Blender drivers, ShaderToRGB, DQS/B-Bones и cloth не считать автоматически перенесёнными
  через FBX. Для каждого различия сохранять результат адаптации и пределы проверки.

## Архитектура игры

- Runtime — C++/Unreal assets; Python, MCP и PowerShell нужны для разработки/подготовки,
  но не должны быть зависимостью готовой игры.
- Разделять VR-ввод/трекинг, перемещение, контакты, выбор реакции, анимацию/мимику,
  звук, вторичную физику и меню. Контакт сообщает событие; конкретный персонаж
  определяет ресурсы реакции.
- Модель, клипы, физический ассет, semantic bone/morph mapping, зоны, таймеры,
  capabilities и бюджеты физики хранить в редактируемом CharacterProfile Data Asset.
- Не добавлять Gratia-specific имена костей/морфов, пути ассетов, размеры сцены
  или количество тел в универсальную игровую логику.
- Отсутствующие возможности другой модели отключать предсказуемо и диагностировать.
  Не подменять отсутствие морфа, кости или клипа успехом.
- Выбор цели должен быть явным: ссылка/регистрация/selection API. Не опираться
  на случайного «первого актора» при нескольких персонажах.
- Настройки, полезные художнику/разработчику, должны быть доступны в Details/Blueprint.
  Сложную математику держать в небольших C++-компонентах; анимационное представление
  предоставлять через редактируемый профиль/Animation Blueprint.
- Данные экземпляра не менять в общем Data Asset во время игры.
- Editor-only импорт/генерацию отделять от runtime. Test/soak инфраструктуру
  отделять от основного игрового координатора.

## Ввод, контакты и физика

- Для ввода проверять всю цепочку: raw controller value → Input Action/context →
  разрешение движения → collision result → фактическое движение Pawn.
- Диагностика должна явно различать zero input, missing asset/context/player,
  menu blocked, collision blocked и tracking unavailable. Ограничивать частоту логов.
- Контакт допускается только после устойчивого трекинга и завершения восстановления.
  При потере трекинга удержание отменяется.
- Разделять raw target контроллера и ограниченную видимую руку. Контактные зоны
  и collision proxies — разные данные.
- Проверять sweep при быстрых движениях, старте на/внутри поверхности, пересекающихся
  прокси, скольжении и смене позы. Не заменять CCD только конечным overlap.
- При выключении вторичной физики сохранять безопасные прокси рук/тела и позу.
- Основную позу/ноги держать управляемыми; вторичную физику ограничивать группами,
  суставами, damping и бюджетами. Не включать весь скелет как свободный ragdoll.
- Проверять NaN/Inf, аномальное отклонение и безопасный сброс. Учитывать tick ordering
  и отложенное создание физических приводов.

## Git, сборки и воспроизводимость

- Использовать Git для исходников, настроек, Unreal assets и документации.
  Изменения фиксировать осмысленно; не переписывать пользовательскую историю.
- Unreal assets/Blender/textures хранить через Git LFS. Не коммитить Saved,
  Intermediate, Binaries, Builds, DDC, логи, runtime-зависимости или токены.
- Не выводить конфиги/командные строки с секретами целиком.
- Каждая сборка должна иметь build id, commit/source state, fingerprint ассетов,
  версию движка и время сборки. Проверки ссылаются на конкретный manifest.
- Отмечать расхождение текущих исходников и собранного exe. «Последняя версия»
  должна означать конкретный идентификатор.
- Поддерживать одну документированную активную pipeline; старые скрипты явно помечать
  историческими. Подготовительные операции должны быть повторяемыми и сохранять ресурсы.

## Проверки и отчётность

- Проверять независимую математику automation-тестами, интеграцию — игровыми тестами,
  финальные ресурсы — готовой сборкой, реальные устройства — VR-журналом/метриками.
- Не считать hand=-1/demo событие доказательством реального касания.
- Новую модель проверять отдельным профилем с другим скелетом; замена цвета/материала
  той же Gratia не является проверкой переносимости.
- При изменении логики запускать относящиеся к ней проверки и регрессию готовой сборки.
  Не расширять тестирование без причины после успешного результата.
- Сохранять логи/снимки/метрики и описывать наблюдаемые ограничения без догадок.
- 90 FPS подтверждать вместе с GPU/CPU и статистикой доставки/репроекции SteamVR
  в смешанном сценарии; короткий idle-прогон не является финальной приёмкой.
- Перед завершением обновлять GratiaVR/README.md, docs/ и фактический статус MVP.md.
- Не добавлять лишние системы ради абстракции. Новая граница/интерфейс должны решать
  конкретную задачу поддержки, настройки, тестирования или замены модели.
